# OPC AI OPERATING SYSTEM v1.0
## IMPLEMENTATION PACKAGE
### MODULE 2 — PERMISSION PROFILES

**Document ID:** OPC-IMPLEMENT-002  
**Version:** 1.0  
**Status:** Draft for Founder Approval  
**Applies To:** AI Chief of Staff + 5 Executive Agents + Specialist Agents

---

# 1. PURPOSE

Permission Profiles define what an Agent is actually allowed to do at runtime.

They MUST be evaluated independently from:

- role;
- intelligence;
- tool availability;
- technical capability;
- domain ownership.

Core principle:

`Capability ≠ Authority`

---

# 2. PERMISSION ACTION MODEL

Recommended permission verbs:

- READ
- SEARCH
- ANALYZE
- CREATE_DRAFT
- RECOMMEND
- REVIEW
- REQUEST_APPROVAL
- APPROVE
- EXECUTE
- MODIFY
- DELETE
- ESCALATE
- VERIFY

Not every Agent receives every verb.

---

# 3. PERMISSION STATES

Each action MAY be assigned one of:

### ALLOW
Agent may perform autonomously.

### ALLOW_WITH_CONDITIONS
Agent may act if specified conditions are satisfied.

### DRAFT_ONLY
Agent may prepare but cannot finalize or execute.

### REVIEW_ONLY
Agent may assess but not alter.

### APPROVAL_REQUIRED
Agent may proceed only after valid approval.

### ESCALATE_ONLY
Agent cannot act directly.

### DENY
Action is prohibited.

---

# 4. PERMISSION PROFILE OBJECT

Each Permission Profile SHOULD include:

- Profile ID
- Agent ID
- Business Scope
- Legal Entity Scope
- Environment
- Capability
- Resource
- Action
- Permission State
- Conditions
- Approval Authority
- Financial Limit
- Risk Limit
- Data Scope
- Tool Scope
- Effective Date
- Expiry
- Version

---

# 5. SCOPE DIMENSIONS

Permissions SHOULD be scoped by:

- Agent
- Business
- Legal Entity
- Geography
- Customer
- Project
- Workflow
- Data Type
- Financial Threshold
- Risk Level
- Environment

Avoid broad global permissions where narrower scope is practical.

---

# 6. ENVIRONMENT SEPARATION

Permissions SHOULD distinguish:

- SANDBOX
- TEST
- STAGING
- PRODUCTION

Production access MUST be more restrictive than testing access.

---

# 7. FOUNDER PROFILE

The Founder retains ultimate reserved authority.

Typical Founder permissions:

- APPROVE strategic decisions
- APPROVE financial commitments
- APPROVE outbound communications
- APPROVE policy changes
- APPROVE major risk acceptance
- APPROVE contracts
- APPROVE production changes
- APPROVE agent permission elevation

Founder actions SHOULD still be auditable.

---

# 8. AI CHIEF OF STAFF PROFILE

Recommended default:

## ALLOW
- READ cross-domain business state
- ANALYZE
- RECOMMEND
- REVIEW
- PRIORITIZE approved work
- ROUTE tasks
- ESCALATE
- VERIFY coordination state

## DRAFT_ONLY
- strategic decision packages
- Founder communications
- cross-agent directives with material external effect

## DENY / RESERVED
- approve spending
- approve contracts
- approve external outbound communication
- waive compliance
- self-elevate permissions

The Chief of Staff coordinates authority but does not inherit Founder authority.

---

# 9. PRODUCT & OFFER AGENT PROFILE

## ALLOW
- READ product/customer/evidence data
- ANALYZE opportunities
- CREATE_DRAFT product concepts
- CREATE_DRAFT offers
- CREATE_DRAFT pricing architecture
- RECOMMEND product changes
- REVIEW validation evidence
- ESCALATE technical/commercial risk

## ALLOW_WITH_CONDITIONS
- modify Product Truth in DRAFT state
- create experiments within approved scope

## APPROVAL_REQUIRED
- launch material product/offer
- material pricing changes
- warranty/SLA changes
- major scope changes

## DENY
- approve financial exceptions
- make external commitments
- override Finance price floor
- override Compliance requirement

---

# 10. SALES & GROWTH AGENT PROFILE

## ALLOW
- READ customer/account/pipeline data
- ANALYZE opportunities
- CREATE_DRAFT outreach
- CREATE_DRAFT proposals
- RECOMMEND pricing/discount
- manage internal pipeline state
- create internal follow-up tasks
- REVIEW account plans

## APPROVAL_REQUIRED
- external outbound communication
- binding pricing/discount exceptions
- credit exceptions
- customer commercial commitment
- contract acceptance

## DENY
- override Product Truth
- approve credit
- approve spending
- promise unvalidated delivery capability
- alter compliance controls

---

# 11. FINANCE & CONTROL AGENT PROFILE

## ALLOW
- READ financial systems
- ANALYZE financial truth
- RECONCILE
- CREATE_DRAFT budgets
- CREATE_DRAFT forecasts
- CREATE_DRAFT payment proposals
- REVIEW deal economics
- REVIEW credit exposure
- RECOMMEND capital allocation
- VERIFY financial records

## APPROVAL_REQUIRED
- accounting adjustments above defined materiality
- policy-defined financial exceptions

## DENY
- self-approve payment
- execute unauthorized payment
- approve own capital request
- change bank instructions without verification
- waive AR/credit controls independently

---

# 12. OPERATIONS & WORKFLOW AGENT PROFILE

## ALLOW
- READ operational state
- create internal tasks
- manage approved workflow state
- monitor SLA
- create procurement requests
- CREATE_DRAFT RFQ
- CREATE_DRAFT PO
- allocate approved internal resources
- pause unsafe automation
- create incidents/exceptions
- VERIFY execution

## ALLOW_WITH_CONDITIONS
- run approved internal automation
- modify low-risk workflow configuration within delegated scope

## APPROVAL_REQUIRED
- PO issuance
- supplier commitment
- material workflow change
- external supplier/customer communication

## DENY
- approve spend
- change financial controls
- renegotiate customer terms
- override product/compliance constraints

---

# 13. STRATEGY & COMPLIANCE AGENT PROFILE

## ALLOW
- READ enterprise data
- ANALYZE strategy/risk/compliance
- CREATE_DRAFT policies
- CREATE_DRAFT risk treatments
- REVIEW contracts
- map obligations
- identify regulatory change
- RECOMMEND strategic decisions
- ESCALATE compliance/legal uncertainty

## APPROVAL_REQUIRED
- policy activation
- material risk acceptance
- compliance exception
- strategic pivot implementation

## DENY
- sign contracts
- waive mandatory law/regulation
- issue legal opinion beyond competence
- approve capital commitments
- self-approve governance changes

---

# 14. SPECIALIST AGENT PROFILE

Specialist Agents SHOULD default to narrower authority than Executive Agents.

Default:

## ALLOW
- READ scoped context
- ANALYZE
- RECOMMEND
- CREATE_DRAFT
- ESCALATE

## DENY BY DEFAULT
- APPROVE
- EXECUTE external side effects
- DELETE
- modify canonical truth directly
- create financial commitment

Privileges MAY be expanded explicitly.

---

# 15. HIGH-RISK ACTION CLASSES

The following SHOULD default to APPROVAL_REQUIRED or DENY:

- payment
- refund
- contract signature
- PO issuance
- credit extension
- pricing below floor
- outbound external communication
- legal filing
- policy exception
- production configuration change
- deletion of canonical data
- access-control change
- secret/credential management

---

# 16. FINANCIAL THRESHOLD CONTROL

Permission MAY depend on transaction size.

Example:

- <= Threshold A: prepare/recommend
- > Threshold A: Founder approval required
- > Threshold B: enhanced review + Founder approval

Thresholds SHOULD live in policy, not hard-coded into Agent prompts.

---

# 17. RISK-BASED PERMISSION

Permission SHOULD also depend on risk.

Example:

Low-risk internal reversible action:
`ALLOW`

Material reversible action:
`ALLOW_WITH_CONDITIONS`

High-impact or irreversible action:
`APPROVAL_REQUIRED`

High-impact + low-confidence:
`ESCALATE_ONLY / HOLD`

---

# 18. TOOL-SPECIFIC PERMISSION

Permissions MUST be mapped to actual tools.

Example:

Gmail:
- SEARCH = ALLOW
- READ = ALLOW
- DRAFT = ALLOW
- SEND = APPROVAL_REQUIRED

Banking:
- READ_BALANCE = ALLOW
- PREPARE_PAYMENT = ALLOW
- EXECUTE_PAYMENT = DENY / APPROVAL_REQUIRED

Database:
- READ = scoped ALLOW
- INSERT = conditional
- UPDATE = conditional
- DELETE = restricted

---

# 19. DATA PERMISSION

Data access SHOULD distinguish:

- Public
- Internal
- Confidential
- Financial
- Personal
- Secret

Agents SHOULD receive only the minimum data required for the task.

---

# 20. DELETE CONTROL

DELETE SHOULD be denied by default for canonical records.

Prefer:

- archive;
- deactivate;
- supersede;
- soft delete;

when audit/history matters.

Hard deletion SHOULD require explicit authority.

---

# 21. PERMISSION ELEVATION

An Agent MUST NOT self-elevate.

Elevation workflow:

`Need → Request → Reason → Scope → Risk → Approval → Temporary Grant → Audit → Expiry`

---

# 22. TEMPORARY PERMISSIONS

Elevated permissions SHOULD:

- have a narrow scope;
- have expiry;
- have explicit purpose;
- be auditable;
- be revoked after use.

---

# 23. BREAK-GLASS ACCESS

Emergency access MAY exist for critical continuity.

It SHOULD require:

- defined emergency condition;
- limited scope;
- strongest feasible logging;
- immediate post-use review;
- automatic expiry.

Break-glass MUST NOT become normal workflow.

---

# 24. SEPARATION OF DUTIES

High-risk processes SHOULD separate:

`Prepare → Review → Approve → Execute → Reconcile`

A single Agent SHOULD NOT control all stages where material risk exists.

---

# 25. SELF-APPROVAL PROHIBITION

An Agent MUST NOT satisfy an approval requirement by:

- approving its own request;
- treating recommendation as approval;
- treating tool permission as approval;
- splitting a transaction;
- routing through another Agent to bypass authority.

---

# 26. PERMISSION DENIAL BEHAVIOR

If permission is insufficient, the Agent SHOULD:

1. stop before side effect;
2. preserve current state;
3. explain blocked action;
4. identify required authority;
5. prepare approval package;
6. escalate.

It SHOULD NOT merely fail silently.

---

# 27. PERMISSION DECISION RECORD

Material permission evaluation SHOULD record:

- requested action;
- Agent;
- resource;
- scope;
- applicable profile;
- applicable policy;
- result;
- approval reference;
- timestamp.

---

# 28. PERMISSION MATRIX

Recommended implementation artifact:

| Agent | Resource | Action | Default State | Approval |
|---|---|---|---|---|
| Chief of Staff | Cross-domain data | Read | ALLOW | — |
| Product | Product Truth | Modify | CONDITIONAL | Domain rules |
| Sales | External email | Send | APPROVAL_REQUIRED | Founder |
| Finance | Payment | Execute | DENY/APPROVAL_REQUIRED | Founder |
| Operations | PO | Issue | APPROVAL_REQUIRED | Founder |
| Strategy | Policy | Activate | APPROVAL_REQUIRED | Founder |

The full matrix SHOULD be machine-readable.

---

# 29. DEFAULT-DENY RULE

Where no valid permission rule exists:

`DENY + ESCALATE`

The system MUST NOT infer permission from ambiguity.

---

# 30. PERMISSION REGRESSION TESTS

Minimum tests SHOULD include:

- unauthorized financial execution;
- external send without approval;
- self-approval;
- transaction splitting;
- cross-business data access;
- expired temporary permission;
- permission elevation without approval;
- unauthorized delete;
- tool capability mistaken for authority;
- break-glass misuse.

All P0 permission tests MUST pass.

---

# 31. IMPLEMENTATION ACCEPTANCE CRITERIA

Module 2 is implementation-ready when:

1. Every Agent has a base Permission Profile.
2. Permissions are separated from System Instructions.
3. Default deny is enforced.
4. Tool permissions map to business authority.
5. High-risk actions have explicit approval states.
6. Financial and outbound actions preserve Founder controls.
7. Data access is scoped.
8. Temporary permissions expire.
9. Permission elevation is governed.
10. Separation of duties is enforceable.
11. Permission decisions are auditable.
12. Regression tests cover authority bypass.
